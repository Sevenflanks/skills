# 系統功能操作說明書製作 SOP

本 skill 僅限使用者明確觸發，不依需求內容自動選用。

適用 Web、桌面、內部業務系統或 API 驅動功能。目標是讓未參與開發者找得到入口、照步驟操作，理解每個欄位／按鈕／icon／狀態、必填與限制，並追溯適用版本與證據。

開始前讀取 [文件與證據契約](references/document-contract.md)，使用其輸入、覆蓋矩陣、章節、檢核表與工作紀錄。產出 DOCX／PDF 或執行 QA／交付時，讀取 [渲染與交付](references/rendering-and-delivery.md)，依環境選工具並保存實際證據。

## 安全與責任

製作者收集版本、程式與實機證據，完成標註、驗證及交付；業務／系統確認人提供範圍、角色與操作授權。帳密、Cookie、token、個資、客戶／保單／財務與內網資訊僅供已授權的環境操作，不寫入文件、檔名、命令輸出或版本庫。截圖優先使用測試資料、遮罩或裁切；需要原始敏感資料交付時先取得同意。

製作手冊不自動授權正式交易、變更權限、送帳、刪除或批次。停在確認前畫面，只有已取得該操作的明確授權才執行。

## 證據蒐集流程

### Step 0：確認範圍與安全邊界

1. 列出所有需要說明的 URL、功能頁籤、彈窗與異常狀態。
2. 明確記錄操作環境及可執行的動作；若會有外部副作用，先停在確認前畫面。
3. 確認交付格式、路徑與是否必須保留原始截圖。
4. 建立工作目錄與本次 `README.md`，先寫下日期、環境、版本範圍與已知限制。

**品質閘門：** 沒有範圍、環境和操作授權時，不開始登入或產生測試資料。

### Step 1：版本與變更盤點

優先從官方 release/tag 或部署資訊確認本次功能對應版本；再以 repository 原始碼補足 UI、欄位與 API 行為。

1. 依 branch 與版本檔推導「正確 tag 家族」，不可只取整個 repository 最新 tag。
2. 取得前端與後端的最新相關 release：tag、發布時間、release notes、目標 commit。
3. 驗證 tag 所指 commit 是否等於目標 branch HEAD；若不一致，文件要清楚寫「文件依 tag」或「文件依 branch」，不能混用。
4. 比較上一版與本版 tag，列出與本次功能有關的 PR／commit 摘要。
5. 以程式碼查出：路由、側欄選單、頁面元件、API 呼叫、欄位驗證、預設值、選單來源與狀態文字。

**最低證據表：**

| 項目 | 必須記錄 |
| --- | --- |
| 前端 | repo、branch、tag、tag SHA、branch SHA、變更摘要 |
| 後端 | repo、branch、tag、tag SHA、branch SHA、變更摘要 |
| 功能定位 | route／URL、選單文字、核心元件或 API |
| 差異結論 | 本文件涵蓋哪些新增、調整或已知未啟用功能 |

**品質閘門：** 禁止只以 release 的 `targetCommitish` 文字判斷已打包；一定要比較 tag SHA 與 branch HEAD。

### Step 3：實機檢視與截圖

1. 使用有授權的帳號登入指定環境；截圖前確認 URL、頁面標題與登入角色。
2. 先截取側邊欄展開畫面，並讓目標選單清楚可見。
3. 逐一走訪覆蓋矩陣的每個區域；每次互動後先讀取最新 DOM 或畫面，確認狀態已改變再繼續。
4. 對於下列情境，至少各保留一張畫面：
   - 預設畫面。
   - 展開查詢條件後的畫面。
   - 有必填標示的建立／編輯表單。
   - 重要彈窗或二次確認。
   - 正常有資料的清單。
   - 無資料、失敗或未啟用狀態（如系統提供）。
5. 原始截圖命名採用可排序格式：`NN_<page>_<state>.png`，例如 `06_create-form.png`。

**截圖準則：**

- 保留足夠上下文，不只裁切單一按鈕；讀者必須能知道該元件位於哪個頁面。
- 讓瀏覽器縮放、視窗大小與語言維持一致。
- 相同表單優先拍完整畫面；無法容納時以連續多張圖呈現，並標示圖號與畫面區段。
- 截圖時不可為了製作文件而送出會造成外部副作用的資料。

### Step 4：視覺標註

為原始截圖建立「標註副本」，不得覆蓋 `assets/raw` 中的原圖。

1. 對於明確需要點擊、輸入或切換的區塊，使用紅色方框標記。
2. 同一張圖有多個操作點時，以紅色圓形編號 `1, 2, 3...` 標記，並在圖說或步驟逐一解釋。
3. 紅框要包住可點擊範圍，而不是只圈圖示中央；避免遮住欄位文字或按鈕名稱。
4. 只有在滑鼠游標本身能增加理解時才加游標 icon；一般情況以紅框加編號較清晰、較易維護。
5. 標註完成後逐一檢查：框線是否正確指向、文字可讀、編號與文件敘述是否一致。

**推薦標記規格：** 紅色 `#E31B23`、外框 4–5 px、內框 1–2 px、圓角 8–10 px、白字紅底編號。

### Step 5：欄位與互動規格整理

資料來源的優先順序如下：

1. 實機 UI（目前使用者真正看得到的內容）。
2. 前端元件（label、required、`type=number`、min/max、預設值、下拉選項、顯示條件）。
3. 後端 API／DTO／驗證規則（格式、長度、業務限制、錯誤訊息）。
4. 已核可的需求規格或業務窗口說明。

每個可互動元件都要分類並說明：

| 類型 | 最低說明內容 |
| --- | --- |
| 文字／數字輸入欄 | 定義、必填性、資料格式、長度／數值範圍、是否可多筆、預設值。 |
| 日期／日期時間欄 | 定義、必填性、格式、起迄關係、預設期間、清除方式。 |
| 下拉／自動完成欄 | 定義、必填性、選項來源、相依欄位、可否複選／搜尋。 |
| Switch／勾選 | 開／關意義、預設值、對畫面或資料的影響。 |
| 按鈕 | 動作、前置條件、是否有確認、成功後結果、是否有外部副作用。 |
| Icon | 圖示名稱、用途、出現條件、點擊後畫面或下載結果。 |
| 表格欄位 | 欄位意義、可否排序、狀態值、分頁與每頁列數行為。 |

**必填判定原則：**

- UI 有 `*`、HTML `required`、前端檢核或後端必填驗證任一成立，即標示為「是」。
- 若 UI 沒有星號但送出時程式明確擋下，仍應標示為「是（送出時檢核）」。
- 不能從證據確定時，寫「待系統／業務確認」，不得猜測為必填或選填。

## 撰寫、QA 與完成條件

依文件契約完成入口、流程、所有互動項目與欄位限制，圖號／紅框編號對應步驟；依渲染與交付契約做結構及逐頁 QA，再核對交付檔。只有版本可追溯、實機截圖與覆蓋完整、QA 成功或受限原因明確、交付位置與 hash／大小核實後才能交付。

依實際 shell 選 pwsh 或 bash；用對應的檔案、編碼、清理及 exit code 語法，工具依環境偵測，不能把單一 renderer 的失敗當成全部不可用。最後回報最終檔、版本／環境／角色、涵蓋功能、實際檢查結果與限制，不回傳未要求的中間產物。

## 維護

將新的可泛化問題修正整理入相關契約；系統專屬 API、URL、帳號、欄位與 release 規則放在該次 profile／附錄。更新後以一個獲授權的新功能驗證「覆蓋矩陣 → 截圖 → 欄位規格 → 渲染證據 → 交付」，不能為了維護自動操作正式系統。
